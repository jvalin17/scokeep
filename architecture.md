
Hash routes = no server config needed, refresh-safe, works on Render.

### Game State Machine

```
LOBBY → BIDDING → CONFIRM_BIDS → PLAYING → ROUND_END → SCORING
                                                          │
                                          ┌───────────────┤
                                          ▼               ▼
                                    NEXT_ROUND        SET_END
                                    (→ BIDDING)     ┌────┴────┐
                                                    ▼         ▼
                                                EXTEND    GAME_OVER
                                              (→ BIDDING)  (→ FINAL)
```

Phase stored in DB. Frontend polls `GET /api/game/:id` to sync phase on load.

## 4. Database Schema

### Tables

```sql
-- Persistent group identity
CREATE TABLE playground (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(50) NOT NULL,          -- funky group name
    pin_hash    VARCHAR(128) NOT NULL,         -- bcrypt hashed 4-digit PIN
    share_code  VARCHAR(8) UNIQUE NOT NULL,    -- auto-generated, URL-safe
    players     JSONB NOT NULL DEFAULT '[]',   -- ["Alice","Bob","Charlie"] ordered
    created_at  TIMESTAMP DEFAULT NOW(),
    updated_at  TIMESTAMP DEFAULT NOW()
);

-- One row per game session
CREATE TABLE game (
    id              SERIAL PRIMARY KEY,
    playground_id   INTEGER NOT NULL REFERENCES playground(id),
    players         JSONB NOT NULL,            -- ordered player list for THIS game
    settings        JSONB NOT NULL,            -- {mode, appearance, timer, scoring, sets, mustLose, trumpRotation}
    current_round   INTEGER NOT NULL DEFAULT 1,
    total_rounds    INTEGER NOT NULL,          -- sets × 8
    phase           VARCHAR(20) NOT NULL DEFAULT 'bidding',
    dealer_index    INTEGER NOT NULL DEFAULT 0, -- rotates each round
    status          VARCHAR(20) NOT NULL DEFAULT 'active', -- active/finished
    started_at      TIMESTAMP DEFAULT NOW(),
    finished_at     TIMESTAMP,
    CONSTRAINT fk_playground FOREIGN KEY (playground_id) REFERENCES playground(id)
);

-- One row per round per game
CREATE TABLE round (
    id          SERIAL PRIMARY KEY,
    game_id     INTEGER NOT NULL REFERENCES game(id),
    round_num   INTEGER NOT NULL,              -- 1-based
    cards_dealt INTEGER NOT NULL,              -- 8,7,6,...,1,8,7,...
    trump_suit  VARCHAR(10) NOT NULL,          -- spades/diamonds/clubs/hearts
    bids        JSONB NOT NULL DEFAULT '{}',   -- {"0": 3, "1": 2, ...} playerIndex → bid
    hands_won   JSONB NOT NULL DEFAULT '{}',   -- {"0": 3, "1": 1, ...} playerIndex → actual
    scores      JSONB NOT NULL DEFAULT '{}',   -- {"0": 13, "1": -11, ...} calculated
    status      VARCHAR(20) NOT NULL DEFAULT 'bidding', -- bidding/confirmed/playing/scored
    created_at  TIMESTAMP DEFAULT NOW(),
    CONSTRAINT fk_game FOREIGN KEY (game_id) REFERENCES game(id),
    UNIQUE(game_id, round_num)
);
```

### Why JSONB for players/bids/scores?

- Player count varies (2-8), no fixed columns needed
- Bids and scores are always read/written as a batch (all players at once per round)
- JSONB allows flexible querying for future analytics (v2)
- Avoids a `player_round` join table — simpler queries, fewer round-trips

### Data Flow Per Round

```
1. BIDDING:
   POST /bid {playerIndex: 0, value: 3}
   → UPDATE round SET bids = jsonb_set(bids, '{0}', '3') WHERE game_id=X AND round_num=Y

2. CONFIRM:
   POST /start-round
   → UPDATE round SET status='playing'
   → UPDATE game SET phase='playing'

3. ROUND END:
   POST /hands {playerIndex: 0, value: 2}
   → UPDATE round SET hands_won = jsonb_set(hands_won, '{0}', '2')

4. SCORING:
   POST /end-round
   → Service reads bids + hands_won
   → ScoringEngine.calculate(bids, hands_won, formula)
   → UPDATE round SET scores={...}, status='scored'
   → UPDATE game SET current_round+=1, dealer_index=(dealer_index+1)%N, phase='bidding'
   → If round was last in set → phase='set_end'
   → If game finished → status='finished', phase='final'
```

## 5. Scoring Engine (Pluggable)

```python
# services/scoring.py

def kachuful_standard(bid: int, actual: int) -> int:
    """Bid 0 made=10, Bid 1 made=11, Bid N≥2 made=N×10, miss=negated."""
    if bid == actual:
        if bid == 0:
            return 10
        elif bid == 1:
            return 11
        else:
            return bid * 10
    else:
        if bid == 0:
            return -10
        elif bid == 1:
            return -11
        else:
            return -(bid * 10)
```

## 6. Trump & Round Sequence

```python
# utils/trump.py

TRUMP_ORDER = ["spades", "diamonds", "clubs", "hearts"]

def get_trump_for_round(round_num: int) -> str:
    return TRUMP_ORDER[(round_num - 1) % 4]

def get_cards_for_round(round_num: int, rounds_per_set: int = 8) -> int:
    """8,7,6,5,4,3,2,1,8,7,6,5,4,3,2,1,..."""
    position_in_set = (round_num - 1) % rounds_per_set
    return rounds_per_set - position_in_set
```

## 8. Security

| Concern | Approach |
|---------|----------|
| PIN storage | bcrypt hash, never stored plain |
| Playground access | PIN verified → session cookie (httponly, secure, samesite) |
| Join live game | Share code only, no PIN needed (by design) |
| CSRF | Token-based for all POST routes |
| Input validation | Pydantic models on all API inputs |
| SQL injection | SQLAlchemy ORM, no raw SQL |
| XSS | No user HTML rendered, JSON API only |

### Rate Limiting

Using `slowapi` (in-memory, no Redis needed):

| Attack | Limit | Lockout |
|--------|-------|---------|
| PIN brute-force | 5 attempts per share code per minute | 15 min lockout after 5 failures |
| Playground creation spam | 10 per IP per hour | Rejected until window resets |
| Global API flooding | 60 requests per IP per minute | 429 Too Many Requests |
| Share code guessing | 8-char alphanumeric = ~2.8 trillion combinations | Practically unguessable |

### Concurrency Guards

Server-side enforcement on every write:

```python
# Every bid/hands submission checks phase
def validate_phase(game, expected_phase):
    if game.phase != expected_phase:
        raise HTTPException(409, f"Game is in '{game.phase}' phase, not '{expected_phase}'")

# Bid submission — reject duplicate for same player
def validate_bid_slot(round, player_index):
    if str(player_index) in round.bids:
        raise HTTPException(409, f"Bid already submitted for player {player_index}")

# End round — require all players have entries
def validate_round_complete(round, player_count):
    if len(round.hands_won) < player_count:
        missing = player_count - len(round.hands_won)
        raise HTTPException(400, f"{missing} player(s) still missing hands_won entry")
```

**Multi-device scenario:**
- Frontend fetches `GET /api/game/:id` before each action — if phase changed, redirects to correct screen
- Last-write-wins for bid edits (acceptable for v1 — handoff, not parallel entry)
- PostgreSQL row-level locking on UPDATE prevents partial writes

## 10. Concurrency Check

- **Single-phone primary use:** No concurrent writes to same round. No conflict.
- **Handoff scenario:** Second phone joins via share code. Risk: two people submit bids simultaneously.
- **Mitigation:** `phase` column acts as a lock — API rejects bid submission if phase ≠ 'bidding'. Last-write-wins is acceptable for v1 (handoff means one person takes over, not parallel entry).
- **DB level:** PostgreSQL row-level locking on UPDATE is sufficient.

### Consistency & Correctness Tests (critical)

These tests verify the app never produces wrong scores or loses data:

| Test | What It Proves | Priority |
|------|---------------|----------|
| **Score math: full game simulation** | Run 3 sets (24 rounds) with known bids/hands → assert final scores match hand-calculated expected values | must |
| **Score math: every formula branch** | Bid 0 made, bid 0 miss, bid 1 made, bid 1 miss, bid 2-8 made, bid 2-8 miss — 14 cases minimum | must |
| **Cumulative score consistency** | Sum of all round scores per player must equal their total on scoreboard — verified after every round in a multi-round test | must |
| **Round data integrity** | After scoring, bids + hands_won + scores JSONB all have exactly N entries (one per player) — no missing/extra keys | must |
| **Dealer rotation consistency** | After 8 rounds with 4 players, dealer should have rotated twice through all players | must |
| **Trump rotation consistency** | Round 1=♠, 2=♦, 3=♣, 4=♥, 5=♠ — verify for 24+ rounds | must |
| **Cards-per-round consistency** | Set 1: 8,7,6,5,4,3,2,1. Set 2: 8,7,6,5,4,3,2,1. Verify for multi-set game | must |
| **Undo restores exact state** | Score round → undo → verify round data cleared, game.current_round decremented, total scores recalculated without that round | must |
| **Undo + redo consistency** | Undo round → re-enter same data → scores must be identical to before undo | must |
| **Must-lose enforcement** | With 5 cards: if bids so far total 4, verify bid value 1 is rejected (would make total=5=cards) | must |
| **Must-lose allows all others** | Same scenario: bids 0,2,3,4,5 should all be allowed | must |
| **Extend game continuity** | Play 3 sets → extend → round 25 should have cards=8, trump continues rotation, dealer continues rotation, scores carry over | must |
| **End game early preserves data** | End game at round 12 → all 12 rounds of data preserved, final scores correct for those 12 rounds | must |
| **Player order preserved** | Reorder players in lobby → bidding queue follows exact same order → scoreboard columns follow same order | must |
| **Flexible total warning** | Enter hands that don't sum to cards dealt → warn but allow → scores still calculated correctly | must |
